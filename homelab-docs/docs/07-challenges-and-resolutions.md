# Challenges & Resolutions

A record of the non-trivial problems encountered building this stack,
each framed as: symptom, root cause, diagnostic method, and fix. Kept
separate from the per-service docs since several of these span multiple
components and are the most transferable part of this project.

---

## 1. Docker install pulled the wrong distro's repository

**Symptom:** `apt install docker-ce ...` failed with
`Unable to correct problems, you have held broken packages.`

**Root cause:** Docker's install script mis-detected this Ubuntu-based
distribution and registered the Debian `trixie` APT repository instead
of Ubuntu `noble`.

**Diagnosis:** Inspected the script's own verbose output, which showed
the exact repository URL it had written to
`/etc/apt/sources.list.d/docker.list`.

**Fix:** Removed the incorrect repo file, manually registered the
correct Ubuntu repo/codename combination, reinstalled.

---

## 2. Pi-hole couldn't bind port 53

**Symptom:** `docker run` for Pi-hole failed immediately with
`failed to bind host port 0.0.0.0:53/tcp: address already in use`.

**Root cause:** `systemd-resolved`'s DNS stub listener already held
port 53 on the host.

**Diagnosis:** `sudo ss -tulpn | grep :53` identified the owning
process.

**Fix:** Disabled `DNSStubListener` in `systemd-resolved`'s config,
repointed the host's own `/etc/resolv.conf` at `127.0.0.1` (where
Pi-hole would bind once started), restarted the service, then started
Pi-hole.

---

## 3. Pi-hole silently rejected LAN queries

**Symptom:** Pi-hole ran without error and resolved queries correctly
from `localhost`, but every other device on the network timed out
querying it.

**Root cause:** Pi-hole's default DNS listening mode only answers
queries it considers local to its own container network, not the
broader LAN.

**Diagnosis:** Compared `dig @127.0.0.1` (succeeded) against
`dig @<host-ip>` from the same machine (also timed out, ruling out a
router/firewall issue) and found the explanatory line in the
container's own logs:
`dnsmasq: ignoring query from non-local network <ip>`.

**Fix:** Recreated the container with `FTLCONF_dns_listeningMode=all`.

---

## 4. Two services fighting over `/etc/resolv.conf`

**Symptom:** All internet access on the host stopped working days after
the Pi-hole and Tailscale setups were both already working individually
— every site failed to load, with no obvious trigger.

**Root cause:** Tailscale's default "accept DNS" behavior rewrites
`/etc/resolv.conf` to point at its own resolver whenever it connects,
silently overwriting the `nameserver 127.0.0.1` entry that had been set
for Pi-hole.

**Diagnosis:** Basic connectivity checks (`ping`) succeeded, which
initially pointed away from a DNS problem; `curl` failing with
`Could not resolve host` narrowed it back to DNS specifically; `cat
/etc/resolv.conf` showed a file explicitly headed
"generated by tailscale."

**Fix:** `sudo tailscale set --accept-dns=false`, then restored the
Pi-hole resolver entry.

**Lesson:** when two independent services can each rewrite the same
system config file, whichever ran most recently wins silently. Worth
checking for this class of conflict early when something that was
previously working stops working with no direct change made to it.

## 5. ProtonVPN's official apt repository had an unmet dependency

**Symptom:** `apt install proton-vpn-gnome-desktop` failed with
`python3-proton-vpn-local-agent (>= 1.6.3) but it is not installable`.

**Root cause:** the required package simply wasn't published in the
repository's package index at the time
(`apt-cache policy python3-proton-vpn-local-agent` showed no candidate
at all).

**Diagnosis:** Ruled out a local misconfiguration by confirming the
package had zero available versions, not merely a version mismatch.

**Fix:** Installed ProtonVPN via its official snap package instead,
which required first removing Linux Mint's default block on snapd
(`/etc/apt/preferences.d/nosnap.pref`) — a deliberate distro choice, not
a bug, so removed intentionally and narrowly for this one package.

---

## 6. Portainer UI deploy silently failed

**Symptom:** Deploying Pi-hole through Portainer's web form appeared to
complete, but no container was created and no error was shown anywhere
in the UI.

**Diagnosis:** `docker ps -a` confirmed no container existed at all
under that name.

**Fix:** Deployed the identical configuration via the Docker CLI
instead, which surfaced the real, actionable error (the port 53
conflict from issue #2) immediately.

**Lesson:** a management UI is not a reliable source of truth for *why*
something failed — the CLI/daemon logs remain the ground truth.
